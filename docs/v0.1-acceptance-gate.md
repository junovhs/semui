# SEMUI v0.1 Acceptance Gate

This document defines how the project decides that the v0.1 round-trip claim is proven.

It ties together:

- [docs/v0.1-fixture-scenes.md](./v0.1-fixture-scenes.md)
- [fixtures/v0.1/manifest.toml](../fixtures/v0.1/manifest.toml)
- [docs/v0.1-supported-css-subset.md](./v0.1-supported-css-subset.md)
- [docs/v0.1-loss-budget.md](./v0.1-loss-budget.md)

## What v0.1 Must Prove

The v0.1 milestone claim is:

`HTML/CSS -> SEMUI -> HTML/CSS` can round-trip the canonical fixture corpus with very little to no loss.

This is proven only when:

- every canonical fixture is materialized and tracked
- every canonical fixture stays within the supported CSS subset
- every canonical fixture passes the structural, computed-style, and visual gates
- no unsupported construct appears in the fixture corpus without being resolved by changing either the fixture or the subset contract

## Canonical Inputs

The acceptance gate uses exactly these source artifacts:

- the five canonical fixture scenes selected in `ACC-02`
- the fixture corpus layout and machine-readable manifest created in `ACC-03`
- the supported CSS subset defined in `ACC-04`
- the loss budget defined in `ACC-05`

No additional scene may affect the v0.1 pass decision unless the acceptance docs are updated intentionally.

## Required Evidence Package

Before v0.1 can be declared complete, the project must produce all of the following evidence for every scene in `fixtures/v0.1/manifest.toml`:

1. Source intake evidence
   - the source HTML and CSS fixture pair used for the run
   - confirmation that the scene only uses in-scope constructs

2. Normalization evidence
   - the extracted SEMUI artifact at the reserved `expected/scene.semui.json` path or its final agreed successor
   - diagnostics showing that no in-scope property was dropped silently

3. Emission evidence
   - the emitted round-trip HTML
   - the emitted round-trip CSS

4. Verification evidence
   - structural diff result
   - computed-style diff result
   - visual diff result
   - any per-scene diagnostics or exceptions

5. Summary evidence
   - a single report that states pass or fail for each scene
   - a single milestone report that states whether the corpus passes as a whole

## Sign-Off Workflow

The sign-off workflow is sequential and strict.

### Step 1: Corpus Lock

The maintainer confirms that:

- the canonical scene list is final for v0.1
- the fixture manifest and source assets are the ones being tested
- the supported subset and loss budget docs are the current source of truth

If any of those move, sign-off resets until the new baseline is agreed again.

### Step 2: Automated Verification

The Rust verification pipeline runs against every fixture and produces the evidence package.

This step fails immediately if:

- a fixture uses unsupported CSS
- an expected artifact is missing
- any structural, computed-style, or visual gate fails

Verification is **read-only**: a normal `cargo test` only compares the freshly
generated artifacts against the committed goldens and never rewrites them, so the
working tree stays byte-for-byte unchanged. After an intentional pipeline change
the maintainer regenerates the goldens through the explicit, opt-in maintenance
path and commits the resulting diff:

```text
cargo test --lib release::tests::proof::regenerate_goldens -- --ignored
```

### Step 3: Human Review

After automated verification passes, a maintainer performs a short human review of the rendered source and round-trip outputs.

The human review checks for:

- layout translation that escaped the numeric thresholds
- text emphasis or hierarchy changes that feel wrong even if metrics look close
- obvious visual regressions in borders, radii, fills, or alignment

Human review is not allowed to waive a failed automated gate.
It only confirms that the passing automated result also looks correct.

### Step 4: Milestone Declaration

v0.1 is declared proven only when:

- every scene passes automation
- human review finds no meaningful drift
- the result is written down in the milestone report or issue resolution

At that point, the claim changes from "expected to work" to "demonstrated to work."

## Who Signs Off

The sign-off roles are intentionally lightweight:

- automation signs off on measurable invariants
- the project maintainer signs off on corpus lock and visual credibility

If the project later grows a larger team, these roles can split further.
For v0.1, one maintainer can perform the human sign-off as long as the automated evidence is preserved.

## Failure Handling

If a scene fails, the project must classify the failure before continuing:

- fixture bug
- subset-contract bug
- parser bug
- cascade or resolver bug
- layout bug
- extractor bug
- emitter bug
- verifier bug

The project does not get to mark the milestone complete while failures remain unclassified or unexplained.

## Exit Criteria for `ACC-01`

The acceptance umbrella issue is complete only when:

- `ACC-02` through `ACC-06` are done
- the acceptance documents are present in `docs/`
- the fixture corpus is present under `fixtures/v0.1/`
- the next implementation issues have a stable acceptance target

That is the point at which the project can begin Rust implementation work without debating what success means.
