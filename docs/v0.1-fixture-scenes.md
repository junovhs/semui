# SEMUI v0.1 Canonical Fixture Scenes

This document selects the canonical scenes for `ACC-02`.

The purpose of the v0.1 fixture set is narrow:

- prove `HTML/CSS -> SEMUI -> HTML/CSS` with negligible drift
- stay inside the static fidelity loop described in [concept.md](../concept.md)
- match a Rust-first implementation path built around parsing, style resolution, layout, extraction, and emission
- exercise the smallest scene set that still stresses the critical normalization boundaries

These scenes are the acceptance corpus design. `ACC-03` will materialize them as concrete test assets.

## Selection Rules

Every chosen scene must be:

- static: no JavaScript behavior, data loading, or runtime mutation
- explicit: final layout must be understandable from HTML and CSS alone
- small: reviewable by a human in one pass
- diagnostic: a round-trip failure should reveal a specific missing capability
- reusable: suitable as a long-lived regression fixture

Every chosen scene must avoid:

- responsive breakpoints
- grid layout
- flex wrapping
- transforms
- filters
- shadows
- pseudo-elements
- pseudo-class states
- animations or transitions
- custom font loading
- external images
- SVG-heavy artwork

## Canonical Scenes

### F01: `profile_card_absolute`

This is the anchor scene from [test.md](../test.md).

Why it is canonical:

- it already expresses the intended strict-compiler workflow
- it covers absolute positioning directly, which is part of the v0.1 roadmap
- it combines text, shape primitives, borders, radius, and button or badge variants in one compact scene

Required coverage:

- scene background color
- absolute positioning
- nested container and child frames
- rounded rectangle and circle primitives
- border width and color
- explicit `box-sizing`
- text content with resolved typography
- fill colors and text colors
- badge and button variants

### F02: `stacked_info_card`

A compact vertical card with:

- outer container
- title
- body text
- small metadata line
- one inline accent pill

Why it is canonical:

- isolates simple vertical stacking without the distraction of absolute placement
- forces consistent text metrics across heading, body, and metadata roles
- keeps border, radius, and fill interactions in play

Required coverage:

- vertical stack semantics
- intra-card spacing expressed without layout ambiguity
- multiple text styles in one container
- background fill plus inner accent surface
- pill radius and border-box behavior

### F03: `action_row_variants`

A simple horizontal action row composed of:

- a neutral container
- two or three sibling actions
- one solid primary action
- one outlined secondary action
- one quiet text-like action rendered as a low-emphasis button

Why it is canonical:

- tests side-by-side alignment and horizontal stacking
- exposes drift in button sizing, label centering, borders, and radius
- keeps variant fidelity visible without introducing interactivity beyond static visuals

Required coverage:

- horizontal stack semantics
- fixed-height controls
- centered labels
- fill versus outline variants
- consistent radius and border treatment across siblings

### F04: `nested_panel_inset`

A two-level panel scene with:

- an outer card
- an inset panel inside it
- a short heading
- a value block
- a compact status marker

Why it is canonical:

- checks nested surfaces and border layering
- makes box model mistakes easy to spot
- exercises containment without needing complex browser layout behavior

Required coverage:

- nested rectangles with independent fills
- border layering
- inner padding expressed through explicit layout choices
- compact text plus small status decoration
- radius inheritance or override behavior

### F05: `typography_specimen`

A text-led scene with:

- heading
- supporting paragraph
- muted caption
- short highlighted label

Why it is canonical:

- isolates text fidelity from shape-heavy layout
- gives the round-trip loop a clean way to detect drift in font size, weight, line height, and color
- keeps the corpus honest about typography being a first-class part of resolved visual truth

Required coverage:

- font family fallback recording
- font size differences
- weight differences
- line-height differences
- foreground color differences
- width-constrained text blocks

## Why These Five

The set is intentionally small.

Together these five scenes cover the v0.1 promise from [concept.md](../concept.md):

- `profile_card_absolute` covers explicit coordinates and the highest-density static scene
- `stacked_info_card` covers vertical stack normalization
- `action_row_variants` covers horizontal stack normalization and variant fidelity
- `nested_panel_inset` covers nested surfaces and border-box correctness
- `typography_specimen` covers text fidelity in isolation

If the system can round-trip these scenes with negligible drift, it has exercised the minimum believable v0.1 surface.

## Ordering and Priority

Priority order for later materialization and verification:

1. `profile_card_absolute`
2. `stacked_info_card`
3. `action_row_variants`
4. `nested_panel_inset`
5. `typography_specimen`

`profile_card_absolute` is mandatory. The other four complete the v0.1 acceptance picture and should not be dropped unless the milestone definition itself changes.

## Boundaries for Later Issues

What `ACC-02` decides:

- the exact scene families that define v0.1 acceptance
- the stable scene identifiers to use in fixtures, tests, and reports
- the deliberate exclusions that keep v0.1 tractable

What `ACC-02` does not decide:

- the exact file layout for fixture assets
- the golden artifact format
- the loss budget thresholds
- the verification harness design

Those belong to `ACC-03`, `ACC-05`, and `VER-01`.
