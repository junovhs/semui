# SEMUI v0.1 Loss Budget and Diff Metrics

This document defines how much drift is allowed for the v0.1 proof:

`HTML/CSS -> SEMUI -> HTML/CSS`

The goal is not byte-for-byte reproduction.
The goal is negligible visual and structural loss on the accepted fixture corpus.

The canonical fixtures are defined in [docs/v0.1-fixture-scenes.md](./v0.1-fixture-scenes.md), materialized under [fixtures/v0.1](../fixtures/v0.1/README.md), and constrained by [docs/v0.1-supported-css-subset.md](./v0.1-supported-css-subset.md).

## Acceptance Model

Every fixture is evaluated through three gates:

1. structural diff
2. computed-style diff
3. visual diff

A fixture passes v0.1 only when all three gates pass.

## Gate 1: Structural Diff

Structural diff compares the normalized source scene against the normalized round-trip scene.

### Required invariants

These must match exactly:

- scene identifier
- visible node count
- node ordering within each parent
- text node content
- native control kind for controls such as `button`
- primitive shape kind when it is explicit in the fixture contract

### Allowed normalization noise

These differences are acceptable at the structural layer:

- class names change
- selector names change
- CSS rules are split or merged
- declaration order changes
- shorthand properties expand into longhands
- omitted default-valued declarations are not re-emitted

### Structural failure conditions

Any of the following is a failure:

- a visible node is added or removed
- text content changes
- a button becomes a non-button or the reverse
- a shape primitive changes kind, such as circle to rounded rectangle
- an extra wrapper is introduced that changes layout or creates a visible artifact

## Gate 2: Computed-Style Diff

Computed-style diff is the primary correctness gate for v0.1.

The verifier should compare normalized computed snapshots for every visible node in the supported subset.

### Exact-match properties

These must match exactly after normalization:

- `position`
- `display`
- `box-sizing`
- `flex-direction`
- `align-items`
- `justify-content`
- `align-self`
- `cursor`
- text content
- font weight
- fill colors
- border colors
- foreground colors

### Tolerance-based properties

These may differ only within the listed tolerance:

- `top`, `left`, `width`, `height`, `min-width`, `margin`, `padding`: `<= 1px`
- `gap`: `<= 1px`
- `border-width`: `<= 1px`
- `border-radius`: `<= 1px`
- `font-size`: `<= 1px`
- `line-height`: `<= 1px`

### Accepted computed-style normalization noise

These are acceptable and should normalize to equivalence:

- `background` versus `background-color`
- `border: 0` versus explicit zero-width border longhands
- `font-family` list formatting differences that preserve the same fallback sequence
- omitted zeros when the resulting computed value is unchanged
- equivalent hex color casing

### Computed-style failure conditions

Any of the following is a failure:

- an in-scope property differs beyond tolerance
- an in-scope property is dropped without an explicit diagnostic
- a value is replaced by a materially different supported value
- unsupported input is silently coerced into a lossy supported value without reporting it

## Gate 3: Visual Diff

Visual diff is the final proof that the round-trip preserved the approved appearance.

The verifier should render the source and round-trip scenes under the same fixed conditions:

- same viewport size
- same device pixel ratio
- same default browser font environment
- no hover, focus, or active state

### Visual pass thresholds

A fixture passes the visual gate only when all of the following are true:

- total differing pixels are `<= 0.5%` of the rendered scene
- no contiguous diff region exceeds `8x8px`
- no diff region shifts a text block, control, border edge, or primitive boundary by more than `1px`

### Accepted visual noise

The only acceptable visual drift is edge-level raster noise such as:

- anti-aliasing fringes along curves or glyph edges
- one-pixel edge variance that does not change geometry, readability, or hierarchy

### Visual failure conditions

Any of the following is a failure:

- text appears to move, wrap differently, or change emphasis
- a control changes size or alignment perceptibly
- a border, radius, or fill region changes shape perceptibly
- the scene background or nested panel colors shift materially
- a diff cluster indicates a real layout translation rather than edge noise

## Unsupported Construct Policy

The canonical v0.1 fixtures should contain only in-scope constructs.

That means:

- unsupported constructs in fixture inputs are a fixture-authoring error
- unsupported constructs in ad hoc user inputs are allowed only if diagnostics report them explicitly
- unsupported constructs never count as silent acceptable loss

For the v0.1 fixture corpus, unsupported input is an automatic failure until the fixture or subset contract is corrected.

## Per-Scene Reporting Contract

The future Rust verification harness should emit one report per scene containing:

- structural pass or fail
- computed-style pass or fail
- visual pass or fail
- unsupported construct diagnostics
- a short summary of the first failing node or region

This report can later back `VER-01` and `REL-01`.

## Milestone Pass Rule

SEMUI v0.1 is acceptable only when:

- every canonical fixture passes all three gates
- no fixture relies on unsupported CSS
- all deviations are either exact matches or listed normalization noise
- there is no unclassified drift left to interpretation

The standard is intentionally strict.
v0.1 should prove that SEMUI can round-trip a bounded CSS subset with very little to no loss, not merely produce something similar.
