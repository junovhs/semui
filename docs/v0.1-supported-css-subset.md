# SEMUI v0.1 Supported CSS Subset

This document defines the CSS and layout surface that counts toward the v0.1 fidelity promise.

It is intentionally smaller than "CSS in general."

The goal is to support exactly the static surface needed for the v0.1 round-trip proof:

- `HTML/CSS -> SEMUI -> HTML/CSS`
- negligible visual drift on the canonical fixture corpus
- a Rust-first implementation path that can be built incrementally

This subset is the contract for `PAR-01`, `CAS-01`, `LAY-01`, `EXT-01`, `EMIT-01`, and `VER-01`.

## Scope Definition

For v0.1, a scene is in scope only if it uses:

- static HTML
- static CSS
- no JavaScript execution
- no responsive breakpoints
- no pseudo-class or pseudo-element state
- no animation or transition behavior
- an explicit zero body margin; emitted scenes canonicalize the same page frame

The canonical fixtures live under [fixtures/v0.1](../fixtures/v0.1/README.md) and are the concrete examples of this subset.
The executable selector/property/value mapping is
[`fixtures/v0.1/coverage.json`](../fixtures/v0.1/coverage.json); corpus tests
reject missing or stale mappings.

## Supported HTML Surface

The v0.1 fixture and acceptance surface supports these element families:

- structural containers: `div`
- text blocks: `h1`, `p`
- inline helpers: `span`
- native controls with explicit reset styling: `button`

This is not an exhaustive parser limit for the future system.
It is the accepted HTML surface for the v0.1 proof.

## Supported Selector Surface

Selectors in scope for v0.1:

- type selectors: `body`, `h1`, `p`, `button`
- class selectors: `.card`, `.button`, `.meta`
- simple compound selectors: `button.primary`, `.button.secondary`
- comma-separated selector groups where each member is individually supported

Selectors out of scope for v0.1:

- id selectors
- attribute selectors
- pseudo-class selectors
- pseudo-elements
- sibling combinators
- child combinators
- descendant chains longer than one simple subject lookup
- `:not(...)` and other functional selectors

The intent is to keep selector matching trivial and deterministic in the first Rust implementation.

## Supported Layout Surface

### Positioning

Supported:

- normal document flow
- `position: absolute`
- `top`
- `left`

Out of scope:

- `right`
- `bottom`
- `position: relative`
- `position: fixed`
- `position: sticky`
- `z-index`

### Display Modes

Supported:

- block flow via default layout
- `display: flex`
- `display: inline-flex`

Supported flex subset:

- `flex-direction: row`
- `flex-direction: column`
- `align-items: center`
- `justify-content: center`
- `gap`
- `align-self: flex-start`

Out of scope:

- `display: none` (Scene IR v0.1 has no hidden-node display state)
- wrapping
- `flex-grow`
- `flex-shrink`
- `flex-basis`
- `justify-content` values other than `center`
- `align-items` values other than `center`
- `align-content`
- `order`
- grid layout

## Supported Box Model Surface

Supported:

- `box-sizing: border-box`
- `width`
- `height`
- `min-width`
- `margin`
- `padding`
- `border`
- `border-radius`

Constraints:

- lengths are `px`
- border usage is limited to explicit solid borders
- acceptance fixtures should prefer fully explicit sizing over implicit content sizing

Out of scope:

- percentage sizing
- viewport units
- `calc(...)`
- `max-width`
- `max-height`
- per-side border style variations
- outline
- overflow management

## Supported Paint Surface

Supported:

- `background`
- `background-color`
- `color`
- six-digit hex colors

Out of scope:

- gradients
- images
- multiple backgrounds
- opacity
- filters
- box shadows
- blend modes

## Supported Typography Surface

Supported:

- `font-family`
- `font-size`
- `font-weight`
- `line-height`
- `font-family: inherit`

Constraints:

- acceptance fixtures use explicit fallback stacks such as `Inter, sans-serif`
- text should be encoded as plain text nodes, not generated content
- line-height should be explicit where fidelity matters

Out of scope:

- custom webfont loading
- letter spacing requirements
- text transforms
- text decoration
- multi-font fallback normalization beyond the provided stack

## Supported Native Control Surface

Buttons are in scope only when their browser defaults are neutralized explicitly.

Supported:

- `appearance: none`
- explicit border, background, size, padding, radius, and typography on `button`
- `cursor: pointer`

Out of scope:

- default platform button rendering
- focus rings
- hover or pressed states
- disabled state styling

`appearance` is a source-boundary reset, not a Scene IR field. The resolver
accepts only `none`, and the emitter writes that canonical reset for every
control. Other `appearance` values are unsupported and produce diagnostics.

## Supported Value Forms

Value forms in scope:

- numeric pixel lengths such as `8px`, `24px`, `320px`
- integer font weights such as `400`, `500`, `600`, `700`
- keyword values used by the fixture corpus such as `absolute`, `flex`, `inline-flex`, `border-box`, `center`, `row`, `column`, and `inherit`
- `none` only as the supported `appearance: none` control reset
- hex color literals

Everything outside this value surface is treated as unsupported until explicitly added to the acceptance contract.

## Parsing and Normalization Expectations

For v0.1, the Rust implementation should be able to:

- parse supported HTML and CSS without loss of source order
- match the supported selector surface
- resolve the supported property set into explicit computed values
- normalize layout into explicit geometry for the supported positioning and flex subset
- emit diagnostics whenever an input scene uses out-of-scope constructs

Each canonical scene declares its accepted diagnostic set in
`expected/diagnostics.txt`. Blank lines and `#` comments are ignored. Any
remaining line is a stable diagnostic key:

- `unsupported-property:<property>`
- `unsupported-value:<property>=<value>`
- `unsupported-selector:<selector>`

Release proof compares these files to analyzer output and fails on any missing
or unexpected diagnostic. An expectation file containing only a comment
explicitly declares that the scene must produce no diagnostics.

The v0.1 system does not need to emulate a full browser.
It needs to make the accepted subset explicit and reproducible.

## Fixture-to-Subset Mapping

- `profile_card_absolute`: absolute positioning, explicit frames, border-box, buttons, badge, typography
- `stacked_info_card`: column flex stack, text hierarchy, pill styling, borders, radius
- `action_row_variants`: row flex stack, button variants, centered labels
- `nested_panel_inset`: nested surfaces, border layering, compact status marker
- `typography_specimen`: text metrics, color fidelity, width-constrained blocks
- `update_toast`: absolute placement, column flex layout, badge, button reset, typography

The role-tagged coverage fixtures added in `COR-01` exercise the same subset
exhaustively rather than introducing new constructs:

- `supported_contract_micro`: every supported selector form, property, and value family in one minimal scene
- `settings_row_real`, `metric_tile_real`: minimized real-world scenes within the subset
- `unsupported_selectors_negative`, `unsupported_declarations_negative`: out-of-scope constructs that must produce diagnostics

The executable mapping is `fixtures/v0.1/coverage.json`; corpus tests fail on a
missing or stale entry. If a future fixture requires properties beyond this
list, that is a scope change and must be recorded intentionally rather than
absorbed silently.

## Non-Goals for v0.1 Acceptance

The following are explicitly not part of the v0.1 fidelity promise:

- browser-complete CSS support
- responsive behavior
- scripting and event semantics
- accessibility state styling
- animation fidelity
- generated content
- visual effects beyond flat color and borders

This boundary is deliberate.
v0.1 exists to prove the static round-trip loop, not to impersonate the full web platform.
